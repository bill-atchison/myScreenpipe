01Intent & why

The Owner works mostly inside a Parallels Windows 11 VM on a Mac: MultiTerminal, Warp, Claude Code and Codex. They want one screenpipe, on the Mac, to record that work in a way that shows which app and which project it belongs to. Today that takes two screenpipes. The second one runs inside the VM and costs CPU, and the Owner wants it gone.

What the Mac records today, from a sample of 81 Parallels frames:

  • Text is already good. Every frame has OCR text, about 3,100 characters on average. screenpipe falls back to OCR when accessibility returns nothing.
  • The labels are useless. The app is Parallels Desktop and 80 of 81 window names are Windows 11. Nobody can tell MultiTerminal from Chrome, or one project from another.
  • MultiTerminal never says which project you're in. Its window title stays fixed at MultiTerminal - REST API: Running on port 5050, even though it already knows the focused pane's project and ticket.

02Goals, non-goals, anti-goals

Goals

  • Mac frames of the VM carry the real Windows app name and window title in app_name / window_name, so search, the timeline and activity summaries group work properly.
  • MultiTerminal's window title shows the focused pane's project and ticket, so the label above carries the project.
  • The VM's screenpipe can be turned off, leaving one recorder in total.
  • The VM-side helper uses negligible CPU and memory.

Non-goals

  • Screen text, UI Automation text, keystrokes or audio from inside the VM. The Mac already captures all of these through the VM window. (Owner default; they may revisit.)
  • Browser URLs from inside the VM, and Coherence-mode-specific handling. Both are possible later additions.
  • Titles that terminal programs set inside MultiTerminal's tabs. They never reach the Windows window title, and MultiTerminal's own title covers the project.

Anti-goals: a failure even if it works

  • Exposing the Mac's screenpipe API beyond the Mac itself, for example to the corporate LAN.
  • Delaying, dropping or blocking any capture. Recording is the critical path (AGENTS.md).
  • Mislabelling frames: putting VM context on frames when Parallels isn't the frontmost Mac app, or when the context is stale.
  • Letting a relabelled frame slip past the user's privacy filters.

03Constraints

  • Network: the Mac API listens on 127.0.0.1:3030 only, and every request needs the bearer API key, including from localhost (server.rs:1597-1601). The only built-in way to widen it is --listen-on-lan (0.0.0.0, no allow-list), which is ruled out.
  • Existing VM→Mac SSH: the VM already reaches the Mac over the Parallels network with the passwordless key ~/.ssh/id_ed25519_mac (alias mac, set up for the build loop).
  • Hot paths: do_capture in event_driven_capture.rs runs for every frame. Changes there must not block, must not take locks, and must not add allocation for non-Parallels frames.
  • VM toolchain: it has .NET 10 SDK and Windows OpenSSH 10.2. It has no Rust 1.94 (pinned) and no sccache, so native screenpipe crates can't be built on the VM.
  • MultiTerminal repo rules (.claude/CLAUDE.md): agents never launch or kill MultiTerminal.exe, builds go to staged output, only the human deploys, and TreatWarningsAsErrors is on.
  • Fork hygiene: changes are additive, so upstream merges stay clean. event_driven_capture.rs is a hot upstream file, so the hook there stays small and the logic lives elsewhere.

04Approaches

ApproachHowTrade-off
A. VM context helperpicked A tiny Windows background program sends the foreground app and window title to the Mac screenpipe, which relabels its Parallels frames. Accurate, and works in normal window mode. A small new program plus a Mac-side route and hook.
B. Coherence + titles Run Parallels in Coherence so each Windows app becomes a Mac window, and parse titles on the Mac. No VM program, but it changes how the Owner works and only gives titles.

For the network path, the Owner chose an SSH tunnel, reusing the existing key, over a new Parallels-only listen address or --listen-on-lan.

05Decided how

5.1 Data flow

Windows VM                                    macOS host
-----------------------------------------     ----------------------------------------------
vm-context-helper.exe                         screenpipe (127.0.0.1:3030, API key required)
  foreground app + window title                 POST /context/external  -> latest ExternalContext
  on change, plus a heartbeat every 2 s          do_capture: frontmost == Parallels Desktop
  -> http://127.0.0.1:3031/context/external        and context fresh (<= 5 s, Mac clock)
       |                                           and this monitor hosts focus
  ssh -N -L 3031:127.0.0.1:3030 mac  ======>       => app_name / window_name := Windows values
  (supervised by the helper)                     -> privacy filters -> paired_capture -> DB

5.2 Mac side: screenpipe engine myScreenpipe

  • A new route, POST /context/external, registered next to /add. It is behind the existing auth middleware and has no new auth path. Body: { "source": "parallels-vm", "app_name": "MultiTerminal", "window_title": "…", "seq": 42 }. It validates that strings are bounded (e.g. 512 chars for app, 1024 for title) and that source is known. It stores the result, stamped with the Mac's own receive time (no reliance on the VM clock), in a process-global ArcSwap<Option<ExternalContext>>. It returns 204. An empty app_name clears the context.
  • A capture hook: one call, right after metadata is resolved in do_capture (≈ event_driven_capture.rs:3587) and before the lock-screen, privacy, filter and DRM gates. A pure function, e.g. external_context::override_for(app_name, monitor_hosts_focus, now) -> Option<(String, String)>, does an atomic load with no lock. It returns a replacement only when all of these hold:
    • the resolved app is the Parallels VM window app;
    • the context is at most 5 s old;
    • the monitor hosts focus.
    Otherwise nothing changes and nothing is allocated.
  • Unknown guest app (Owner decision, 2026-11-01): when the context is missing, stale or cleared (helper off, tunnel down, VM locked), the VM window is recorded exactly as today, labelled Parallels Desktop. Ignore rules for Windows apps apply only while the helper is reporting. VM pixels are never masked or skipped for lack of context, because recording comes first. The include list keeps matching the host app, so a user with an include list must list Parallels Desktop to record the VM, as today.
  • Privacy: because the override runs before the gates, the user's ignore and include lists, incognito detection and DRM checks see the Windows app and title. Ignoring "Chrome" then also applies inside the VM.
  • Settings: no new setting builder's call, noted. Without a helper posting, the route is inert and the hook never matches. The ticket asked for "behind a setting", but an inert-by-default route meets the intent with less code.
  • Bounds and focus checks keep the original host app. See 5.5: overriding them would turn frames into placeholders when URL allow-lists are on.

5.3 VM side: vm-context-helper myScreenpipe

  • Language: C# on .NET 10, as a single-file, framework-dependent console app run windowless (WinExe). Rust would match screenpipe, but the VM can't build the pinned toolchain. C# is the Owner's home language, and the SDK is already installed.
  • Location: tools/vm-context-helper/ in the fork. It is not part of the cargo workspace or the app build. It is documented in PERSONAL.md.
  • Foreground tracking: event-driven via SetWinEventHook, using EVENT_SYSTEM_FOREGROUND plus EVENT_OBJECT_NAMECHANGE on the foreground window, so title changes are caught. There is no busy polling. It copies the logic of screenpipe's get_focused_app_window_lightweight (screenpipe-a11y/src/platform/windows.rs:2287): GetForegroundWindow, the process image name with UWP/ApplicationFrameHost handling, and GetWindowTextW. Transient shell windows are skipped.
  • Sending: it posts on every change and sends a heartbeat every 2 s, so the Mac's 5 s freshness holds while you sit in one app. When the VM locks or sleeps, posts stop, the context goes stale, and the Mac falls back to Parallels Desktop.
  • Tunnel: the helper starts and supervises ssh -N -o ExitOnForwardFailure=yes -o ServerAliveInterval=15 -L 3031:127.0.0.1:3030 mac, restarting it with backoff. If the tunnel is down, posts fail quietly and are logged at a low rate. They are never retried in bulk; only the latest state matters.
  • API key: read once from %APPDATA%\vm-context-helper\api-key, a file with a user-only ACL. The Owner copies it in using screenpipe auth token on the Mac. It is never logged.
  • Start-up: a per-user Task Scheduler entry at logon, with an install script that the Owner runs once.

5.4 MultiTerminal title myMultiterminal

  • Replace the one-time title (MainForm.cs:1511) with a formatter. With a focused pane: MultiTerminal — {project} · {pane name}: {task title} (REST API :5050). With none, it keeps today's text.
  • Inputs: _lastActiveTerminal as the source of truth for focus (ActiveDocumentChanged misses WebView2 clicks), and the project and task values that TerminalDocument.UpdateStatusBar already computes (:3296-3334).
  • Refresh: when _lastActiveTerminal changes and when that pane's status bar refreshes. Only write Text when the string actually changes.
  • Delivery: its own ticket and branch in myMultiterminal, verified with the repo's build and test commands. The Owner deploys it.

5.5 Hardening from review builder check + Codex

Risk foundResolution
A fresh label lands on older pixels. The guest switches app between the screenshot and the hook. Read the context's seq before the screenshot and again at the hook. If it changed, don't override; the frame keeps Parallels Desktop.
Port hijack leaks the key. Another process holds 3031, the forward fails, and an HTTP post reaches that process. The forward binds 127.0.0.1:3031 explicitly, with ExitOnForwardFailure=yes. The key is sent only after a check through the tunnel: an unauthenticated GET /health must answer as screenpipe. Sending stops as soon as the ssh child exits.
The route works with auth off. The auth middleware is bypassed when api_auth is disabled (server.rs:1611). The route returns 403 unless API auth is enabled. Tests cover auth disabled, a missing token and a wrong token.
Stale or reordered posts. Each helper start picks a random epoch, and seq strictly increases within it. The Mac accepts a post only if it is newer: a new epoch, or a higher seq in the same epoch. Expiry uses the Mac's monotonic clock and is cleared on Mac sleep/wake. The helper sends one request at a time and keeps only the latest pending state.
Lock and sleep keep the context alive. The helper handles WM_WTSSESSION_CHANGE: on lock it posts a clear and pauses heartbeats; on unlock it samples again.
Losing the bounds kills OCR. With URL allow-lists, a mismatched focused-window-bounds check gives a placeholder frame (:3739), not a full-frame OCR as 5.2 said. The override changes only the stored labels and the inputs to the privacy filters. The bounds and focus checks keep using the original host app. A ponytail note in the code records why.
Consumers of app_name. Meeting detection, the AX denylist, browser URL. The AX denylist keys on the host process name and doesn't change. Meeting detection and browser-URL lookup keep the host values. Only labels and the privacy filters see guest values.
MultiTerminal focus. _lastActiveTerminal isn't updated on tab switches (MainForm.cs:7575). Title focus combines tab activation and terminal clicks, and is cleared when a non-terminal or closed pane is active.
Helper process hygiene. The ssh child sits in a Job Object, so it dies with the helper. Key auth needs no passphrase, and known_hosts already trusts mac; ssh runs with BatchMode=yes, so it never prompts. The key is re-read after a 401.

5.6 Verification

  • Mac unit tests, cargo test -p screenpipe-engine, run on the Mac:
    • override_for: fresh, stale, wrong app, monitor not focused, cleared context;
    • route validation: bounds, unknown source, empty clears.
  • MultiTerminal: a unit test for the title formatter, plus the repo's standard dotnet test.
  • Helper: dotnet build, plus a --once flag that prints the current foreground app and title, for manual checks.
  • End to end, with the Owner:
    • with the helper running and the VM's screenpipe stopped, switch between MultiTerminal, Warp and Chrome in the VM;
    • Mac frames show those app names and titles;
    • MultiTerminal frames show the project and ticket;
    • with Parallels not frontmost, or the helper stopped for more than 5 s, frames say Parallels Desktop again.
  • Cut-over: once verified, the Owner turns off the VM's screenpipe autostart.

06Left to the builder

  • The exact macOS app_name string for the VM window (Parallels Desktop vs prl_client_app). Confirm it on the Mac, and match on a small constant list.
  • The exact names, file and module for external_context inside screenpipe-engine, and the route's handler location (routes/).
  • Whether a context change should also fire a capture trigger, if the engine already has a cheap way to ask for one. Without that, in-VM app switches are caught on the next normal trigger.
  • The helper's logging format and log location, and the backoff numbers.
  • The precise MultiTerminal refresh call sites, and trimming long task titles.
Privacy note. Window titles can contain secrets. A recorded PowerShell title held a GitLab token on 2026-11-01. This design carries titles to the Mac just as the VM's screenpipe already did, and the Mac's privacy filters still apply. A better title-redaction rule is out of scope here, but worth a follow-up ticket.
