Overview

Goal: when Parallels is the frontmost Mac app, Mac screenpipe frames carry the foreground Windows app and window title, which a small helper inside the VM reports.

Architecture: a new external_context module in screenpipe-engine holds the latest context, with epoch/seq ordering and a 5 s freshness window on a monotonic clock. A new authenticated route, POST /context/external, feeds it. A small hook in do_capture attaches guest labels for storage only, plus a guest ignore/incognito check. Every admission and processing decision keeps the host values. A C# .NET 10 helper in the VM tracks the foreground window through WinEvent hooks and posts through a supervised ssh -L tunnel.

Tech stack: Rust (axum, arc-swap, tokio), crate screenpipe-engine. C# .NET 10 WinExe using Win32 P/Invoke and Windows OpenSSH.

Out of this plan: the MultiTerminal title (spec 5.4) lives in another repo and gets its own ticket and plan. Nothing here depends on it.

Global constraints

  • The Mac API stays on 127.0.0.1:3030; never --listen-on-lan. The tunnel binds 127.0.0.1:3031 in the VM.
  • The route returns 403 unless API auth is enabled (AppState.api_auth), and 204 on success.
  • Bounds: app_name ≤ 512 chars, window_title ≤ 1024 chars, and source must be "parallels-vm". An empty app_name clears the context.
  • Freshness: at most 5 s by the Mac's monotonic clock. Helper heartbeat every 2 s.
  • Host app matched for an override: "Parallels Desktop", case-insensitive (seen in Mac frames on 2026-11-01).
  • Unknown guest app: the frame is recorded as today, labelled Parallels Desktop. VM pixels are never skipped or masked for lack of context (Owner decision).
  • Hot path: on a miss the hook does one atomic load and no allocation. No locks, no awaits.
  • Native Rust tests run on the Mac (ssh mac, ~/Workspace/myScreenpipe), because the VM has no pinned toolchain or sccache.
  • Rust and TS source files carry the AGENTS.md screenpipe header. C# helper files carry it with //.
Codex review, round 1 (NOT READY → fixed in this revision):
  • Admission must not change. Guest labels are used only for storage and for a separate guest ignore + incognito check. The include list, URL policy, DRM, meeting classification and OCR decisions all keep the host values. This corrects spec 5.2's wording, which said relabelling runs "before the gates". The Owner's intent, "ignore Chrome applies inside the VM, recording comes first", is unchanged.
  • No override on the startup capture, which passes focus ownership as true unconditionally (event_driven_capture.rs:1218).
  • Epochs are ordered (the helper's start time in ms), and a clear keeps a tombstone, so a late or stale post can't revive old context.
  • Tunnel ownership is checked by the owning PID of the 3031 listener, not just a /health response.
  • Tests that touch GLOBAL share one lock. Route tests go through the real router, middleware included.
  • The cargo test command is fixed: it takes one filter.

Review focus

  1. A guest app switch between the screenshot and the hook must give Parallels Desktop, never the new label. Test in Task 3: stale_seq_does_not_override.
  2. Posts arriving out of order (an older seq after a newer one, or a restarted helper with a new epoch) must keep the newest state. Test in Task 1: older_seq_is_rejected and new_epoch_replaces.
  3. The helper stops (VM sleeps or locks): after 5 s, frames say Parallels Desktop again. Test in Task 1: expires_after_five_seconds. Lock handling in Task 4.
  4. API auth disabled, or a missing or wrong token: the route never accepts context. Test in Task 2: rejects_when_auth_disabled, plus the middleware cases.
  5. Port 3031 held by another process: the helper must not send the key. Task 4: --once, the readiness check, and a manual check with a dummy listener.

  2. Run the tests and confirm they fail: dotnet test tools/vm-context-helper.Tests on the VM.
  3. Implement:
    • Foreground: SetWinEventHook on EVENT_SYSTEM_FOREGROUND and EVENT_OBJECT_NAMECHANGE, with a message loop on its own STA thread. Skip transient shell windows, as screenpipe's get_focused_app_window_lightweight does.
    • Sender: one request at a time; a newer state replaces the pending one. POST /context/external with Authorization: Bearer. Heartbeat every 2 s. On a 403, re-read the key once and retry once (the middleware answers 403 for a missing or wrong token); a second 403 logs and waits for the next state change.
    • Tunnel: ssh -N -o BatchMode=yes -o ExitOnForwardFailure=yes -o ServerAliveInterval=15 -L 127.0.0.1:3031:127.0.0.1:3030 mac, started in a Job Object with kill-on-close. Before any keyed send, confirm the listener on 127.0.0.1:3031 is owned by the supervised ssh child's PID (via GetExtendedTcpTable, TCP_TABLE_OWNER_PID_LISTENER). If another process owns it, don't send and log once. Restart with backoff from 1 s up to 60 s. Sending stops on Down.
    • Lock: a hidden window registered with WTSRegisterSessionNotification. On WTS_SESSION_LOCK, publish null and pause heartbeats; on WTS_SESSION_UNLOCK, read the foreground and publish it.
    • Key: read from %APPDATA%\vm-context-helper\api-key and never logged. The log goes to %LOCALAPPDATA%\vm-context-helper\helper.log, at most one line per state change or error, with a 1 MB roll.
